# Performance

Baseline measurements against the targets in `SPEC.md` section 5.6, taken before
the numeric changes of phase C so that each change can be judged against them.

**Recorded:** 2026-11-06, release build, AMD Ryzen AI 7 350 (8 cores), 31 GB RAM,
Windows 11. Rust 1.99.0.

## How to measure

```
cargo bench -p opencalc-core --bench recalc                  # core, 40 runs each
cargo bench -p opencalc-core --bench recalc -- --check       # exit 1 if a budget is exceeded
cargo test --release -p opencalc-app perf -- --ignored --nocapture   # UI frame time
```

`scripts/check.ps1` runs the core benchmark in quick mode with `--check` as a
coarse tripwire. Timings in a debug build mean nothing; only release numbers count.

## Core (evaluator, parser, worker)

Worksheets are generated by `crates/opencalc-core/tests/common`: dimensionally
valid, with units, in shuffled layout order, so layout order is not dependency
order (as in a real worksheet).

| Parse 200 regions | 107 µs | 106 µs | 146 µs | |

| Evaluate 2000 regions | 1.73 ms | 1.61 ms | 2.27 ms | |

## UI

| Workload | Median | Worst | Budget |
|---|---|---|---|
| Frame with 200 visible regions (26% zoom) | **0.76 ms** | 0.89 ms | **16.7 ms** (60 fps) |

This is everything the UI does per frame inside `egui::Context::run`:
typesetting every visible region (there is no layout cache), painting into
shapes, input handling and panel layout. It **excludes tessellation and the GPU**,
which egui does outside `run`, so it is a lower bound on a real frame, not the
whole of it.

## Not measured yet

- Startup to first frame (target under 500 ms): needs a real window.
- Tessellation and GPU time for 200 regions.
- Pan and zoom at 60 fps as a user sees it, as opposed to the work above.

## What the numbers mean

- Every measured target is met by a factor of about 50 to 500. **Incremental
  recalculation (TD-07) is not needed** at these sizes: recalculating the whole
  sheet is already cheaper than a frame. **A layout cache (TD-15) is not needed**
  either. Neither should be built until a measurement says otherwise.
- **Phase C re-measured (2026-11-06, after C2 to C4: complex scalars, matrices,
  unit registry, error locations).** 500 regions 0.41 to 0.60 ms (was 0.39),
  2000 regions 1.82 ms (was 1.73), edit to result 0.18 ms (was 0.15), UI frame
  with 200 visible regions 0.80 ms (was 0.76). About 5 to 15 percent slower,
  and still 300 to 500 times inside the budgets. A matrix-and-complex workload
  (100 regions, each multiplying 3x3 matrices, taking a determinant and doing
  complex arithmetic) takes 0.22 ms, about 2 microseconds a region, with a
  50 ms budget in the benchmark. **Decision: incremental recalculation (TD-07)
  and a layout cache (TD-15) are still not needed.** The numbers to watch are the
  ones the evaluator cannot yet produce: plots, integrals, root finding and
  large user-defined functions, which can take far longer than any region here.
  Those need cancellation (TD-20), not incremental recalculation, and should be
  measured when they land.
- Measured text sizes in document units change slightly with zoom (font rounding
  at small pixel sizes). "Fit" therefore needs two passes to be exact (see
  `perf_frame_time_with_200_visible_regions`). This is a small known imprecision
  (TD-27).
